## Recommendations

- Patch: add import next-step guidance. `import plan` should point to the exact matching `import apply` command; conflict output should name `--on-conflict overwrite` and `--on-conflict fail` so users do not have to search help after seeing a conflict.
- Patch: add a non-interactive guard for `import plan -i` and `import apply -i`. If stdin/stdout is not a TTY, fail fast with a short message suggesting a normal terminal or non-interactive import.
- Patch: validate or reconcile same-cycle `origin/ecosystem/2026-06-02-codex-schema-flags` before release. It addresses current target skill frontmatter/tool lossiness drift; this review does not duplicate that compiler change.
- Minor: ship a first-class project registry before adding `skills install`. The next skill workflow should ask whether a skill belongs globally, to the current project, or to a containing workspace, then route the copied source through normal `plan` and `apply`.
- Minor: add `skills list --all` with scope grouping across global, project, and workspace source. Users should be able to answer "where did this skill come from?" without knowing the on-disk tree.
- Minor: make `workspaces remove` read as "unregister" or add an explicit `--delete-config` option. Today it removes the index entry but leaves workspace-local source config on disk.
- Minor: add `status --fail-on-drift` for CI and scripted checks. Current nonzero status is reserved for errors, which is reasonable for humans but weak as a drift gate.
- Major: design project-scoped installs as a source-of-truth workflow, not as a wrapper around target app folders. Direct installers such as skills.sh-style flows should download into `~/.config/code-agnostic/projects/<name>/skills`, preserve provenance outside strict skill metadata, then preview/apply generated app output.

## Product read

The core global/workspace story is now understandable: source lives under `~/.config/code-agnostic`, users preview with `plan`, then apply generated target output. The main mismatch is local skills. Codex and OpenCode expose project-local skill discovery, and users naturally expect a CLI run from inside a repo to manage that repo's skills. Current `code-agnostic` ignores `.agents/skills` in the current directory, so the product should make project scope explicit before encouraging skill installation commands.

Recovery is improving through same-cycle reliability work, but apply output still does not show the revision id or exact restore command. That is not an alpha blocker today, but it remains a trust affordance worth adding before the CLI feels safe for less expert users.
